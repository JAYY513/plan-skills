# plan-task：任务录入、执行与完成

> 曾用名：new-task（任务录入与拆解）+ task-plan（单任务工作区），两技能已合并为本技能，对话中出现任务信号时自动介入。**hook 可选**：无 hook 时本技能 + 项目 AGENTS.md「计划纪律」仍自动跑完整流程（查命令、开工 `start`、收工 `finish`、对齐门）。hook 只是少打字，不是流程前提。


## 先查命令，再读文件

有 node 时在项目根跑引擎（不要整读 FINDINGS.md / progress.md / INBOX.md）：

| 目的 | 命令 |
|---|---|
| 会话底线（红线+进行中+下一张） | `node <技能目录>/engine/plan.mjs status` |
| 下一张 DoD | `next` |
| 本任务卡片/关联 | `task "<名>"` |
| 结论索引 / 单条全文 | `findings` / `findings --tag X` / `findings --full F3` |
| 未决与疑似已实现 | `inbox` |
| 当前位置 | `ws <slug>` |
| 关联毛病 | `links --orphan` |

## 写入纪律（有 node 时，追加走命令）

追加一条是搬砖，引擎做；判断（标题 / DoD / 结论一段话）仍由你想好、经参数交给引擎——引擎不代写 DoD、不编结论。

| 要追加 | 命令 |
|---|---|
| 新任务 | `task-add "<标题>" --dod "<一句>" [--section 已拆好\|进行中] [--tag X] [--basis F2] [--from "INBOX x"] [--pre "<任务名>"] [--head]` |
| 新结论 | `finding-add --title "<主题>" --source <调研探针\|开发中发现\|失败尝试\|外部输入> --conclusion "<一段话>" [--tag X] [--material <路径>] [--trace <路径>]` |
| 给已有结论补一段 | `finding-add --amend F3 --conclusion "<补充>"`（不新开号；同主题被挡时用这个） |
| 停一个想法 | `inbox-add "<想法>" [--flag 红\|白] [--origin "<来源>"] [--finding F3]` |
| 2-Action 日志 / 当前位置 | `progress-log <slug> [--text "<一行>"] [--kind 进展\|决策\|错误] [--position "<一行>"] [--next "<一行>"]` |

- **追加走命令，不要为了追加一条而整读** TASKS.md / FINDINGS.md / INBOX.md：查重、引用校验、编号、索引再生全在引擎里（写完立刻可查，不等 `finish`）。
- `task-add` 命中已解决 → **退出 0 且没新建**，stdout 是 `已由 X ✅ 实现` 或 `已裁决：<条目>`。**看 stdout**，别只退出码就当新建成功。
- **改 DoD / 挪队 / 删卡仍手改**，手改就要读文件——此时读文件不禁：上面禁的是「为追加一条而整读」。改卡前先问用户（分流第 9 条）。
- 超一段话的内容（notes 章节、对比表、SPEC / ROADMAP、progress postmortem）照旧直接写文件，不进 argv。
- 无 node：本段整条不适用，按各分流条目的手改规则走。

无 node：读 FINDINGS「索引」受管区（`plan-index` 标记内）、TASKS 进行中标题、plan.md「当前位置」。缺失计划文件 → 提示用户先运行 plan-init。

分级（有 node 时按级拉，禁止再造 `context` 命令）：

| 级 | 内容 | 入口 |
|---|---|---|
| 底线 | 红线 + 里程碑 + 进行中一行 + 下一张标题 + 计数 | `status`（session-start 也推这个） |
| 索引 | 编号/日期/标签/状态/主题；INBOX 行；边 | `findings` `inbox` `links` |
| 卡片 | 元数据、DoD、当前位置、关联区 | `next` `task` `ws` |
| 全文 | 原始条目块、progress.md | 各命令 `--full` |
| 材料 | notes/、done/ | 卡片里的路径，直接读文件 |

用户问「跟 X 有关」→ `findings --tag X`；标题不够再 `findings --full F?`。

无 hook 时同样自动（不要等注入）：本会话第一次触及计划（问进度 / 拆任务 / 开工 / 写结论 / 做完了）之前跑 `status`；无 node 则读 SPEC「不做什么（边界）」「技术选型」+ TASKS 进行中标题。收尾或用户说先到这：按完成流程里的两门自检（活跃工作区未 ✅、隔天进行中无工作区痕迹）——不通过先处理，不要当没事。2-Action 照写 progress.md，不要等 pre-tool-use。



## 分流判断


对话中出现以下信号时自动落盘，不等用户点名。FINDINGS 只收已结算结论（含时间盒到期后的「没结论」）。**提问 / 未决选项 / 待确认 / 过程想法 ≠ 结论**，不进热区。

1. **出现调研结论或重要发现** → 写入 FINDINGS.md 热区（落笔前先 grep 索引查重：同主题 → 在原条目追加「补」小节或标记替代，不另开新条目；条目格式：编号、来源、结论含证据、影响标注；只写结论与关键证据）。结论段必须是一段话陈述，不是问句或选项列表。有工作区 `notes/` 时加 `- 材料：.planning/<slug>/notes/`（无材料则整行省略）。过程日志留在 progress.md，用「过程追溯」行引用。**有 node → 用 `finding-add`（标题 / 来源 / 结论三个参数给全；查重、编号、索引再生引擎做，不要为了加一条而 Read FINDINGS.md）**。结论影响计划（改变某里程碑可行性或 SPEC 选型）→ 同步在 INBOX.md 登记一条并引用 FINDINGS 编号，告知用户"已停车，计划变更走 plan-review 时裁决"。未决分流：等人拍板 → INBOX；还要查 → 调研或 notes；过程想法 → progress.md
2. **出现调研材料**（章节 / 对比表 / 大段摘录 / 多来源对照）→ 无工作区则先按调研探针登记并 `--workspace`（对话里直接分析也走这条，不要只留在对话里）。当轮写入 `.planning/<slug>/notes/`：先 `index.md` 一行一条，再分页。禁止把章节写进 FINDINGS 或 progress.md。有材料未写入会丢，但不挡「结论已进 FINDINGS」。notes 没有完成态，可以错、可以改
3. **出现失败尝试**（已经试过、写得出为什么不行，且以后还要避开）→ 写入 FINDINGS.md，来源标"失败尝试"（有 node → `finding-add --source 失败尝试`）。只是猜不行、报错后立刻换方案 → 记 progress.md，不进热区
4. **冒出不服务当前里程碑的新想法 / 待裁决项** → 写入 INBOX.md（有 node → `inbox-add "<想法>" --flag 红|白`，不要再整读 INBOX），标注 🔴（影响当前里程碑）或 ⚪（不影响），告知用户"已停车"，**不要**当场改 ROADMAP.md / SPEC.md；当前里程碑只含 MVP 桶内容时，P0/P1 需求一律停 INBOX.md；服务当前里程碑 → 进 TASKS.md（走下面的录入流程）
5. **出现调研需求** → 登记前先查已有结论（FINDINGS.md 索引、docs/01-wiki、个人知识库），命中则直接引用既有条目、不重复调研。`docs/research` 若已存在只当线索，不当已定论；本体系不往那里写。未命中才进 TASKS.md「调研（限时探针）」区，必须向用户确认时间盒和产出要求（产出默认：FINDINGS.md 一条结论；有章节则加工作区 notes/），缺了就问。时间盒到了：有结论就写结论，没有就写「没结论」+ 原因（这是探针结果，不是把问句当结论）；后面还要实施 → 不要 `finish` 该工作区。调研时优先一手来源（官方文档、源码、论文），二手文章只作线索；没有来源的结论不写进 FINDINGS.md。待确认 / 不定案留 notes 或停 INBOX，不以「有效」进热区。默认把「调研清楚并实施 X」写成一条任务、共用一个工作区
6. **用户问"下一步做什么" / 讨论实施计划要拆任务** → 跑 `next`；队列为空时才从当前里程碑的验收标准反推候选任务（带 DoD），用户确认后录入
7. **用户问"现在什么进度 / 当前状态 / status"** → 跑 `status`（只读不写）
8. **用户说"开工 / 开始做 X"** → 认领任务（调引擎 `start` 命令，见下）；未指定任务名时默认认领「已拆好（待做）」队首；若任务符合工作区判据（见下）→ 传 `--workspace` 自动建 `.planning/` 工作区再动手
9. **继续讨论已录入、尚未开工的任务**（「已拆好」或「调研」区、未标 ✅；任务 = TASKS 上那一条：标题 / DoD / 前置 / 时间盒。`.planning/` 是同一条的施工现场，开工才建，不是第二条任务）→ 默认定稿，卡不动。复述 / 解释 / 闲聊不落盘。发现对话与标题或 DoD 对不上 → 先问一句「要不要改这条任务」，不要默默改、不要再开一条。用户明确要改：改原条目，写后告知；一块塞不进 0.5～2 天 → 拆新任务，需要时写 `- 前置：<旧任务名>`；不想做了 → 从队列拿掉或停 INBOX（还没 ✅，允许动）。已开工、已有工作区：仍是同一条，改范围时同步 `plan.md` 目标与步骤，禁止另开 slug。已标 ✅ 的不走本条：后续要做开新任务，不改 `done/`、不重开旧卡

## 录入流程（进 TASKS.md 的任务）

1. **查重**：有 node → **不用先扫文件**，`task-add` 落盘前自己查完（TASKS 重名 → 退 2 并列已有区名；INBOX 已解决 → 退 0 回「已由 X ✅ 实现」，不建任务），看 stdout 即可。无 node → 扫 TASKS.md（含「已完成」）并跑 `inbox`（必要时 `inbox --resolved` / `--all`）。用户说「做云同步」这类已做过的需求同样走本条。新任务与进行中/已拆好重叠 → 不新增，改为合并/指出现有条目并问用户一句。继续讨论已录入、尚未开工的条目 → 走分流第 9 条，不另开新卡。录入时可写可选行 `- 标签：` / `- 依据：F?` / `- 来自：INBOX x`

2. **检查粒度**：预估超过 2 天 → 拆成 0.5~2 天的子任务，每个可独立完成
3. **生成 DoD**：每条任务写一条可手动验证的完成标准。
   - 差的 DoD："功能能用"
   - 好的 DoD："点击中断 → 输出立刻停止 → 按钮恢复可发状态，手动验证通过"
   写不出可验证句、或切片明显偏大/偏碎时，才对照本仓库一条已 ✅ 任务或上面的例句。不是录入门，不另开语料库。
4. 有 node → `task-add` 追加（默认「已拆好（待做）」**队尾**；用户表达"先做 X / X 紧急"→ 加 `--head` 插**队首**；依赖用 `--pre "<任务名>"`；`--section 调研` 本期不开放——调研任务的时间盒与产出须先向用户确认）。**已在队列里的任务要挪到队首 → 手改**（`task-add` 会按重名退 2）。无 node → 手改，追加到 TASKS.md 对应区域（进行中 / 已拆好 / 调研），挪队首与 `- 前置：<任务名>` 行同样手改。调研后还要实施 → 默认写成一条「调研清楚并实施 X」；必须拆两条时，实施任务抄同一条 `- 工作区：`，调研那条不要先 `finish`
5. **检查队列水位**：「进行中」+「已拆好」合计少于 2 个 → 主动从当前里程碑反推，提议补充任务

## 认领开工与工作区

认领动作由引擎命令完成（在项目根目录执行，任务名按标题精确匹配）：

```bash
node <技能目录>/engine/plan.mjs start "<任务名>"              # 移入「进行中」+ 补开始日期（幂等，重复调不报错）
node <技能目录>/engine/plan.mjs start "<任务名>" --workspace  # 符合工作区判据时加此参数
```

`--workspace` 会自动：从 `assets/templates/` 复制 plan.md / progress.md 到 `.planning/<日期>-<slug>/`、填充任务名与关联条目、在 TASKS.md 任务行下补 `- 工作区：` 关联行（任务与工作区之间唯一的据）；来自「调研」区（或任务块含「时间盒」）时额外复制 `notes/index.md`。已有工作区的任务会复用，目录丢失则按原 slug 重建并自动写 `⚠️ 工作区曾于 … 丢失` 重建标注。

认领前仍由 agent 负责：先扫该任务的 `前置:` 行，前置任务未标 ✅ → 提醒用户一句"X 还没完成，确定要先做这个？"——是提醒不是阻断，用户说继续就继续。

开工前先对照 SPEC 红线（「不做什么（边界）」+「技术选型」）：跑过 `status` 则用其红线行；否则读 SPEC.md 这两节。执行中任何步骤将违背边界或选型（引入被排除的方向、换掉已定技术）→ 先停下与用户确认，不静默漂移。对照判断始终由 agent 负责，不依赖 hook 有没有注入。


是否传 `--workspace` 由以下判据决定（符合任一 → 传，不问用户，建完告知一句；否则普通小任务不建工作区）：

1. 预计跨 ≥2 个会话才能做完
2. 调研型任务（在「调研」区，或执行路径边走边定）——限时探针也必须建，不当小任务跳过
3. 用户明确要求建工作区

多个并行任务各自建独立目录，天然隔离，互不读写。例外：调研与实施共用现场时，实施任务写**同一条** `- 工作区：`，禁止新建第二个 slug。

**node 不可用时的兜底**（罕见，引擎依赖 Node ≥ 18）：按原手动规则执行——任务块移入「进行中」段末尾、补 `- 开始：YYYY-MM-DD`；需建工作区时手动复制模板到 `.planning/<日期>-<slug>/`（slug = 任务名转小写连字符）并补 `- 工作区：` 行；调研型再复制 `notes-index.md` 为 `notes/index.md`。

定位：项目级 5 文件管状态与结论；`.planning/<slug>/` 是单任务的**临时工作区**（`plan.md` + `progress.md` + 可选 `notes/`）。**禁止存放最终结论**——结论的家永远是 FINDINGS.md。详细材料的家是 `notes/`（有材料才建；无完成勾；可以错、可以改）。已验证、以后改代码还要遵守的规则才晋升到 SPEC / AGENTS / wiki。

## 工作区执行纪律

- **每次开工先重读 plan.md**——包括新会话恢复，从「当前位置」接着走，不凭记忆
- **2-Action 规则**：每约 2 次探索 / 修改动作后，把进展、决策、错误落进 progress.md，随手更新 plan.md 的「当前位置」
  - 有 node → `progress-log <slug> --text "<一行>" [--kind 进展|决策|错误]`，收工顺手加 `--position "<进行到哪一步>" --next "<下一步>"`（分别改「当前位置」第 1、2 条）。**不要为了记一条而 Read progress.md 全文**，要看全文用 `ws <slug> --full`
  - 无 node → 手改 progress.md「日志」区（当天 `### 日期` 标题下的 `- 进展：` / `- 决策：` / `- 错误：`）与 plan.md「当前位置」
- **失败路径必须记录**（试过什么、为什么不行），先记 progress.md；只有真试过且以后还要避开的才晋升 FINDINGS
- **步骤不是子任务**：plan.md 的步骤是该（子）任务的执行顺序，不是再拆一遍子任务；步骤不设 DoD——DoD 只在 TASKS.md 的任务行上
- **材料当轮写入 notes/**：出现章节 / 对比表 / 长摘录时先建 `notes/index.md` 再分页；不要等收工，不要写进 progress.md。没有材料不要建空 `notes/`

## 完成流程（用户说"做完了"，或 agent 实测判定 DoD 已满足）

**触发器在状态不在口令**：agent 实测判定 DoD 已满足（或认为任务已完工、想提议下一个任务）时，完成流程即激活，不等用户说"做完了"。提议下一个任务之前，当前任务必须已标 ✅、或已向用户明确声明"暂停"（移回「已拆好（待做）」并记录进展）。分工：**对齐与结论由 agent 先做；机械动作与校验由引擎 `finish` 完成**。不要为此调用 `plan-review`。

1. 逐条核对该任务的 DoD——实际执行验证步骤，不凭印象，全部通过才算完成；标 ✅ 前把本次改动的 diff 自查一遍：只含本任务相关改动，无顺手带入的无关修改
2. 工作区有 `notes/` 且还要改材料、或后续还要实施 → **拒绝 `finish`**。结论可先落 FINDINGS（调研完成 ≠ 工作区归档）；告知一句「工作区先别冻进 done/」
3. **对齐门**（调 `finish` 之前必做）。以 **DoD 实测** 为准，不以 `plan.md` 原计划为准。对不上 / 拿不准未决 / 红线未确认 → 拒绝 `finish`，先改 FINDINGS 或问一句。
   - **对应**：FINDINGS 结论必须对得上实测。中途改了实现 → 改结论或追加「补」，禁止旧结论入库
   - **覆盖**：重读 progress.md 日志「决策 / 错误」（无工作区则扫本会话）。**默认不晋升**；只有以后改代码还要遵守的才进 FINDINGS（新条或「补」），其余在该条旁标明「不晋升结论」。不扫 notes 全不全
   - **材料**：FINDINGS 若有「材料」行，路径必须能打开（活目录或 `done/`）
   - **冲突**（出口互斥；沿用写前确认 / 写后告知，完成时不另开问法）：

     | 类型 | 处理 | `finish` |
     |---|---|---|
     | 知识库内部（重复、新证据推翻旧结论、日志与 FINDINGS 字面不一致） | 自己合并 / 标「已被 F? 推翻」，写后告知 | 过 |
     | 影响计划（里程碑可行性、SPEC 选型、验收标准不再成立） | FINDINGS 写实；INBOX 停一条并引用 F 编号（🔴 当前里程碑 / ⚪ 不影响）；不改 ROADMAP/SPEC | 过 |
     | 拿不准（相反结论分不出对错，且说不清是否影响计划） | 问一句「哪条算数」；用户不在 → 停 INBOX ⚪ | 挡 |
     | 红线未确认（FINDINGS 与 SPEC 红线打架，执行期未获点头） | 🔴 停 INBOX。用户已说过「这次就这样」→ FINDINGS 记下例外 | 挡 / 过 |

   - **无新结论**：无工作区 → 任务行写「本任务无新结论」，不硬造 FINDINGS。有工作区 → 写 FINDINGS 存根（结论只写「本任务无新结论」，不要塞问句或待决）+ 过程追溯，postmortem 指向该编号
   - **INBOX 核销**：任务块有 `- 来自：INBOX x` 时 `finish` 写 `- 已解决：<任务名> ✅（日期）`（留在待裁决，不移区）。也可用 `finish "<名>" --resolve "<INBOX标题>"`。并入里程碑 / 归桶 / 删除未做的仍是 plan-review。不要再手工移入「已裁决」

4. 若该任务有 `.planning/` 工作区 → agent 先写好三合一的内容部分（见下）
5. 调引擎完成校验与机械动作：

```bash
node <技能目录>/engine/plan.mjs finish "<任务名>"
node <技能目录>/engine/plan.mjs finish "<任务名>" --resolve "<INBOX标题>"
```

   校验通过 → 自动把任务移入「已完成（待归档）」、标题加 ✅、补完成日期、回写 `- 结论：F?`、按来自/`--resolve` 写 INBOX 已解决行、再生 FINDINGS 索引、工作区移入 `.planning/done/`；校验不通过 → 列出缺失清单并拒绝标 ✅，agent 补齐内容后重跑。完成后 agent 在任务行补一句「实际怎么做的」（无新结论则该句即「本任务无新结论」）

6. **不许删除**——归档是 plan-review 的职责
7. 检查队列水位，不足则提议补充
8. 向用户输出对齐卡（冲突行三选一；红线未确认走「已停车」且本步未调 `finish`）：

```
对齐 <任务名>
- 对应：<F? 对得上实测 ｜ 已改 FINDINGS>
- 覆盖：<已晋升 / 标明不晋升>
- 材料：<路径能打开 ｜ 无>
- 冲突：自己解决 F? / 已停车 INBOX（🔴|⚪）F? / 待你一句：哪条算数
- 本任务：F? ｜ 无新结论
```

**node 不可用时的兜底**：对齐门 + 三合一核完后，手动把任务块移入「已完成（待归档）」、标题加 ✅、补 `- 完成：YYYY-MM-DD`，手动把工作区目录移入 `.planning/done/`。

### 完成三合一动作（一个动作三件事）

有工作区则缺任何一件，**不许**把任务标 ✅：

1. **结论回填 FINDINGS.md**：按条目格式写入（无新结论则写存根），并加一行引用：`过程追溯：.planning/done/<slug>/progress.md`（至少一条带此行）。有 `notes/` 时把「材料」行改成 `.planning/done/<slug>/notes/`（活跃期写 `.planning/<slug>/notes/`）
2. **固化 postmortem 头**：在 progress.md 顶部 postmortem 区填写——结论 → FINDINGS 编号、一句话坑总结（详情在 FINDINGS）、声明"本文档为过程记录，结论以 FINDINGS 为准"
3. **整个工作区移入 `.planning/done/`**：归档后只读，永不修改（由 `finish` 命令自动执行）。引擎不审 notes 是否写全

收尾两门（agent 必做；有 stop-gate hook 只是代跑同一套，无 hook 时自己查）：门①——存在活跃工作区但关联任务未标 ✅（按 plan.md「关联 TASKS 条目」精确匹配，postmortem 已固化兜底）→ 先补齐或提醒，不要当会话已干净；门②——「进行中」仍有任务且无任何工作区痕迹 → 同样处理，但**开始日期 = 今天的任务豁免**。不是第二套规则。


## 关联技能

- 完成对齐门（FINDINGS 对得上交付、冲突出口）是本技能职责，不走 `plan-review`
- 计划变更（改 ROADMAP / SPEC / 验收标准）、里程碑交接、INBOX 裁决（并入里程碑 / 归桶 / 删除未做的）→ 走 `plan-review`（事件驱动的计划变更门）。任务完成时核销"已被本任务解决"的 INBOX 条目是本技能职责（见对齐门）
- 计划体系未初始化 → 提示用户先运行 `plan-init`
- 项目已有实施调研技能（`.agents/skills/` 下 platform-research / impl-research 一类）→ 机制设计或「怎么实现最好」先走该技能；落盘仍按本技能
- 需要生成这类技能 → `research-init`；没有用户声明的参考源就不要生成
- 不依赖任何外部技能：DoD 实测核对、对齐门、diff 自查、调研一手来源等纪律均已内置在上述流程中

## 纪律

- 不凭空发明任务；拿不准归属就问用户一句，不要猜
- 宣布"做完了 / 下一步做 X"前，当前任务必须已 ✅ 或已显式暂停（移回「已拆好」并记进展）；完成流程由 agent 实测判定触发，不依赖用户口令
- 已录入尚未开工默认定稿：继续讨论不自动改卡；范围 / DoD 对不上先问「要不要改这条」。要改改原条目。`.planning/` 是同一条的现场，不是第二条任务
- 对齐门未过不许调 `finish`；知识库冲突自己改，影响计划停 INBOX，拿不准才问一句
- 「已拆好（待做）」的位置即顺序——调序就是挪条目位置，不设优先级标签、不编号；「进行中」「调研」「已完成」区不排序
- 不修改 ROADMAP.md / SPEC.md——那是 plan-review 的职责
- FINDINGS 只收已结算结论；提问 / 未决 / 待确认 / 过程想法不进热区。失败尝试必须真试过。对齐门覆盖默认不晋升
- 调研结论不落 FINDINGS.md 就不算调研完成。notes 没有完成态；有章节当轮写入 notes/，不写入会丢，但不挡调研完成
- 有 `notes/` 还要改、或还要实施 → 不许 `finish`。不要调研先归档再另开实施任务
- 不要给不需要的任务建工作区——小任务建工作区本身就是腐化。不要给没材料的非调研任务建空 `notes/`
- `.planning/` 活跃区建议 gitignore，`.planning/done/` 提交入库（完成历史不删）；因此材料必须当轮写入 notes/
