## 计划纪律

### 自动落盘判断矩阵

对话中出现以下信号时，按矩阵自动落盘，不等用户点名：

| 对话信号 | 自动动作 | 是否需确认 |
|---|---|---|
| 讨论蓝图 / 愿景 / 做不做什么 / 技术选型 | 更新 SPEC.md 草稿 | 写前确认 |
| 讨论阶段计划 / 里程碑 / 验收标准 | 更新 ROADMAP.md | 写前确认 |
| 讨论新需求 / 新功能 | 按 MVP/P0/P1 归桶到 ROADMAP 范围分层（P1 可先进 INBOX） | 写前确认（改 ROADMAP） |
| "接下来做 X" / 拆任务 / 讨论实施步骤 | 录入 TASKS.md（带 DoD） | 不问，写后告知一句 |
| 继续讨论已录入、尚未开工的任务 | 默认不改卡；对不上先问「要不要改这条」；要改则改原条目，不要另开 | 改卡前问一句 |
| 已结算的调研结论 / 真试过的失败尝试 | 落 FINDINGS.md（一段话结论） | 不问，写后告知 |
| 提问 / 未决选项 / 待确认 | 不进 FINDINGS；未决停 INBOX，还要查进 notes / 调研 | 不问，写后告知 |
| 调研材料（章节 / 对比表 / 长摘录） | 写入该任务 `.planning/<slug>/notes/` | 不问，写后告知 |
| 跨会话大任务开工 | 自动建 `.planning/<slug>/` 工作区 | 不问，写后告知 |
| "做完了" / 任务收尾 | 对齐门 → 三合一 → 标 ✅；知识库冲突自己改；影响计划停 INBOX | 拿不准问一句；改 ROADMAP/SPEC 仍走 plan-review |
| 想法不服务当前里程碑 | 停进 INBOX.md（标注 🔴/⚪） | 不问，写后告知 |

### 纪律

- 执行层（TASKS / FINDINGS / INBOX / .planning/）全自动，写后告知一句即可；锚（SPEC）和路标（ROADMAP）写前必须确认
- SPEC 的「不做什么（边界）」与「技术选型」是执行期红线：配置了 hook 的平台（Claude Code / Codex）会在会话开始时自动注入；无 hook 时（OpenCode / 未配置 / 已禁用）开工前主动读 SPEC.md 这两节对照。执行中若某步会违背边界或选型（如引入被排除的方向、换掉已定技术），先停下与用户确认——这是防「隐式漂移」的护栏
- 规则细节见对应技能：任务录入、开工、工作区、完成（含对齐门）→ plan-task；计划变更、里程碑交接、INBOX 裁决 → plan-review。本文件不复述规则条文
- 体系也要演化：plan-review 收尾会做「体系自检」（纪律执行度 + 文件使用率 + 演化提案）；平时发现某条纪律执行不下去 / 某文件没人看 → 随手记 INBOX 一条"体系问题"，留待自检时裁决
- FINDINGS 只收已结算结论（含探针「没结论」）；提问、未决、待确认、过程想法不进热区。失败尝试必须真试过
- 已录入尚未开工的任务默认定稿；继续讨论不自动改卡。`.planning/` 是同一条任务的现场，开工才建
- 详细调研正文在 `.planning/<slug>/notes/`（可以错、可以改，无完成勾），不进 FINDINGS 正文；结论仍只落 FINDINGS.md
- `.planning/` 活跃工作区建议加入 gitignore；`.planning/done/` 提交入库，归档后永不修改
