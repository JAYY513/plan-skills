# <技能名>：实施前调研

给一个施工问题配齐参照系，回答「怎么实现最好」。**调研 ≠ 实施**：不产出实现代码，只产出带来源的方案。

落盘走 plan-task：结论 → FINDINGS.md（一段话 + 关键证据）；对比表 / 证据账本 / 出处清单 → 该任务 `.planning/<slug>/notes/`；影响计划 → INBOX.md。不要另写 `docs/research/`，不要把章节塞进 FINDINGS。

## 非目标

- 不写实现、不改 `src/`
- 不改 SPEC.md / ROADMAP.md（计划变更走 plan-review）
- 不做泛泛科普——每条结论落到「本项目这一步怎么做」
- 无来源的结论不进 FINDINGS

## 证据深度

先给候选结论分级，再决定读多深：

- **承重**：会决定模块边界、并发、状态机、持久化、协议、错误恢复、安全、许可证或公共契约。必须同时有：① 本项目约束出处；② 一个真实实现锚点（文件:行或符号）；③ 该实现的一个调用方、消费方或行为测试。缺任一项标 `待确认`，不得写成推荐。
- **普通**：命名、目录、非关键默认值。导航层已有精确源码定位且无冲突可采用；定位失效或靠推断 → 按承重处理。
- **冲突 / 高风险**：数据丢失、竞态、跨进程恢复、协议边界，或两源不一致。再核验第二个独立实现或官方文档；不能交叉验证则保留冲突，不定案。

定点核验用「一机制一纵切」：实现主体 → 一个上游调用点 → 一个测试或下游消费点。能确认职责、状态转移、失败语义即停。只有委托、生成代码或冲突才继续下钻。

## 流程

1. **锁定问题**：施工步 / spec / DoD，做什么、不做什么；边界不明先问。
2. **查已有**：FINDINGS 索引、任务 notes/、wiki 索引。命中则引用，只补缺口。
3. **定维**：用本项目会翻车的机制维（<维度列表，或：按任务临时定，不要为凑数发明维>）。维可以少。
4. **路由 + 纵切**：先 L1 列出锚点，再按证据深度进 L2/L3；L4 只补缺口。
5. **对比与裁决**：候选 ≥2 时按**机制维**列表，不要按仓库列。意图加权，不按票数。允许组合（写明谁出哪块）或自研（写明比各源好在哪）。工程难 → 写先做哪一刀，仍是「做」。
6. **最小实现**（若问题是「这一步做多大」）：纵向切片完整（端到端可验证），横向范围可裁。砍广度，不砍链路完整性。
7. **落盘**：FINDINGS 一段话结论（含 1～3 个关键出处）+ 材料指针；notes/ 写对比表、证据账本（机制 / 源 / 锚点 / 调用或测试 / 状态）、出处清单。影响计划则 INBOX 引用 F 编号。

## 质量门

- 时间盒默认 2 小时；到点有结论写结论，没有写「没结论」+ 原因。后面还要实施 → 不要 `finish` 该工作区。
- 每个推荐有出处；承重推荐必须 source-verified。
- 观察与推荐混写、只读一家就定案、无文件:行的「参考某仓」→ 打回。
- 全仓扫描不计入更高质量。

## 反模式

- 把多数派做法当裁决理由
- 把「好读」当「相关」
- 把参考仓机制连同不适用的约束一起抄过来
- 用难做 / YAGNI / 只有 N 家有，把已证实的用户能力写成跳过
